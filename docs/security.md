# Security and privacy

The optional client heartbeat stores only bounded status metadata: a client-generated installation UUID, display/host labels, app version, mode, separate client-reported timestamps, queue counts, and capped project folder/workspace labels. The authenticated credential ID, actor ID, server receive time, and coarse source network bucket come from the server request. Client-reported values are untrusted and informational; they never affect ACL checks, authorization, search, or model context. Presence expires after seven days and the latest-value store is pruned on reads and writes.

MDB trusts the local host, not imported documents or tool arguments. The SDK binds `ActorContext` once. The local CLI represents the owner; HTTP MCP resolves each bearer credential to a server-side actor and scoped permissions before creating tools or returning content. The optional legacy HTTP token still maps every holder to one process actor; prefer one scoped credential per agent. Do not expose an owner CLI or owner-bound SDK as an untrusted remote service. Document text cannot supply identity or permissions.

Workspace ACLs and optional collection restrictions govern access. Global areas require their own capabilities. Read, write, history, promotion and purge authority are distinct. Authorization precedes document metadata, snippets, search scoring, references, context assembly and model inputs. Missing/forbidden object access avoids confirming protected existence. An unrestricted `OWNER` actor is intended only for trusted local administration.

Agent credentials that need the owner's accepted preferences and reviewed shared knowledge can use `mdb credential permissions-template --agent [--workspace ID[,ID...]]`. The recommended permissions are workspace read/write for specifically chosen workspaces plus `global:profile:read`, `global:shared:read` and `global:wiki:read`. `workspace:create` is optional. Do not grant `global:discoveries:read` or any global write permission to routine agents. Each workspace also needs a matching vault `workspace grant`; credential permission ceilings do not replace vault grants. `credential rotate` issues a new credential id and token, so update the consumer's token file and restart its agents. This step does not rotate live credentials.

The dashboard-managed ChatGPT keyed gateway is an explicit broader exception: its by-name credential receives read/write access to reachable workspaces and `global:profile:read/write`. Those names are selectors, not secrets. Anyone who can reach the tunnel and holds its inbound key can read or write the exposed memory. The connector-wide write toggle and per-workspace switches default ON; turn them off in the Connectors panel to refuse gateway writes. Each accepted write is a Vault revision attributed to the gateway actor and can be restored using normal Vault history/restore operations. The narrow `engram_chat_record` operation stores bounded redacted inert text in `personal/chat`; Dream and profile extraction mask assistant/tool turns and cite exact source revisions and user spans. See `docs/chat-integration.md` and `docs/dashboard.md`.

SessionStart checks profile, shared and wiki read capabilities independently and emits only the authorized section. Accepted profile projection excludes sensitive items. Shared/wiki digests include only reviewed promoted/validated shared records and accepted active wiki pages; candidates, unvalidated discoveries, pending proposals and unaccepted insights are excluded. Cached context is separated by credential fingerprint and bound to the section set and content revision; cache is stale-labelled, expires after 24 hours by default, and is purged on auth refusal. The Codex plain-text stdout response has a unit snapshot, but live host injection remains unverified.

Remote credentials may carry the separate `workspace:create` permission. It is never inferred from ordinary workspace scopes or wildcard-free permission ceilings; owner credentials already have owner authority. `engram_workspace_ensure` is exposed only by the `remote-web` toolset. It creates a validated lowercase project slug only when missing, grants read/write to the calling actor alone, and records actor, workspace and time in `.mdb/workspace-create-audit.jsonl`. Existing workspaces return `exists` only when that actor already has read and write access; otherwise the operation refuses and directs the caller to the owner. The default per-principal automatic creation cap is 25 and can be set by the owner with `MDB_AUTO_WORKSPACE_CAP` (1–1000). Slugs use ASCII lowercase letters, digits and hyphens, up to 40 characters; collisions are never auto-renamed because that could bind the project to ambiguous memory.

## Inputs and evidence

Imported Markdown, original attachments, copied KB documentation and model output are untrusted data. MDB never executes their instructions. Paths are validated against traversal, absolute-path writes and symlink escapes. Existing vault symlinks are rejected by safe-path operations. These checks do not replace OS isolation against a malicious privileged process racing filesystem operations.

Generated knowledge requires accessible exact revision evidence. A proposal cannot use unavailable/private cross-scope evidence to publish globally. Shared knowledge must be a separately reviewed sanitized promotion. Source revisions and originals remain unchanged. Prompt instructions remind providers of this boundary, but schema validation, authorization and explicit review enforce persistence rules. Review establishes acceptance, not factual truth.

Wiki retire, restore, rename and merge follow the same review boundary: agents may propose, but only the trusted host may approve or reject through actor-bound SDK/CLI operations. MCP exposes proposal creation, visible proposal listing and read-only revision diff; it exposes no wiki-change approval/rejection or direct delete tool. Proposal listing checks read access to the target and every merge source. Proposal creation and approval check write access for every touched page. Each commit uses Vault with expected revisions; merges checkpoint and resume individual target/source operations, and a changed source is never tombstoned.

The reviewed-proposal gate applies to the new `wiki_change` proposal tools and model-assisted wiki engine. Direct writes continue to follow ordinary ACL grants: an actor with workspace `write` access can call `mdb_patch` / `engram_patch` with `status: "deleted"` to retire a page without creating a wiki proposal. This capability was verified through the SDK with a credential-bound agent. The change is journaled as a new revision, remains available in history, and can be restored through Vault operations; applications that require every retirement to receive proposal review must withhold direct write grants from those agents.

## Capture and providers

Automatic capture is disabled by default and requires consent both when the server registration is created and when a host hook is installed. Claude Code and Codex send only selected lifecycle fields to the authenticated capture endpoint. The remote client writes a minimized, redacted delivery spool under `~/.Engram-remote-spool`; bearer credentials are read from the environment and never stored there. Observation text receives a limited pattern-based secret redaction pass; it cannot guarantee removal of all secrets. Review selected input before enabling capture.

No model/provider means no model calls. The trusted host configures a built-in provider in `mdb.yaml` or supplies one through the SDK; the CLI and MCP host load that configured provider. A configured provider may send supplied documents outside the machine if it does so. MDB ships no hosted provider implementation. Restrict the actor and provider's network execution environment accordingly. Semantic embeddings are unavailable in this MVP.

## Disk and erasure limits

Local-owner direct filesystem access bypasses application ACLs. Revisions, current views, journal, SQLite indexes, intelligence queues, exports and backups can contain private text; restrict disk access and use OS encryption where required. Indexes are not a privacy boundary simply because they are disposable. Purge cannot erase external input files or arbitrary backups/replicas; retain and delete those under a separate operational policy.

HTTP MCP is self-hosted and bearer-authenticated, but does not terminate TLS itself; use HTTPS at a trusted proxy or network layer. Credentials scope actor identity and permissions, and server-side workspace ACLs still govern every read/write. The server spool is durable within the canonical local vault; remote shared access is not multi-region replication or a distributed transaction. See `verification/` and tests for exercised attacks and remaining coverage; do not infer universal security from a passing local suite.

Replica fork installation is guarded by an internal capability passed only through the replication library to Vault. It accepts only an existing local provisional candidate chain whose first parent is the declared common base, and only in the enrolled writable workspace. It can install the already-authorized server revision as the local current head while retaining candidate bytes as immutable history. It cannot change server state, grant access, fetch external content, or be invoked through CLI/MCP/dashboard inputs. Vault verification checks the fork marker, base, candidate chain, identity and content hashes; a forged marker is reported as corruption.

### TLS reverse proxy (Caddy)

Bind Engram to loopback and terminate public TLS at Caddy. `deploy/Caddyfile` is the supported minimal configuration. Keep bearer tokens in each agent's secret environment; Caddy forwards `Authorization` and the MCP session headers by default. Do not set `MDB_MCP_HTTP_HOST=0.0.0.0` when the service is intended to be reachable only through the proxy. Credential create, revoke, rotation, and failed bearer authorization are recorded in the owner-readable `.mdb/http-credentials.json` audit list; token values and hashes are never included in audit records.

```sh
MDB_MCP_TRANSPORT=http MDB_MCP_HTTP_HOST=127.0.0.1 MDB_MCP_HTTP_PORT=3333 node bin/mdb-mcp.js --root /srv/engram
caddy run --config deploy/Caddyfile
```

Point the sample domain at the deployment and verify the certificate and endpoint with `curl --fail-with-body https://memory.example.com/health`. For an internal-only deployment, use a private CA and install its trust root on every agent machine.

## Model provider boundary

Model output is untrusted. It is schema-validated, bound to supplied evidence, staged as a proposal and committed only by explicit review through `Vault`. Remote providers need `allowNetwork`; requests that include vault content also need `allowPrivateContentToRemote`. Prompts are redacted for secrets; errors never include prompts, bodies or keys. Local Ollama/loopback endpoints are treated as local. Common SSN, email and valid card-number redaction is available for local providers with `model.redactPiiForLocal: true` (or `mdb model set --redact-pii-for-local true`). It is off by default to preserve existing local-model behavior, is pattern based, and is not a complete PII detector. A malicious provider endpoint chosen by the vault owner can still read whatever the owner permits it to receive.

### Explicit built-in embedding download

The built-in bge-m3 provider adds one external network exception: a user-initiated download from the pinned Hugging Face repository. The dashboard first previews the immutable revision, exact files, byte counts and SHA-256 digests; download requires an authenticated session, CSRF protection and password re-authentication. Redirects are limited to `huggingface.co`, `*.huggingface.co`, `hf.co`, and `*.hf.co`, TLS verification remains enabled, and no credentials are sent. Files are downloaded sequentially to a private cache outside the vault and app, verified before atomic installation, and inference then runs offline. Vault content is never sent during download or local inference. Remote embedding endpoints remain separately gated by embedding network and private-content consent.

## Replicas (Phase 1 library)

A replica contains complete Markdown revisions and source-independent metadata for explicitly enrolled workspace scopes. Anyone with local OS access to the replica can read that cached workspace content; v1 does not encrypt it at rest. Removing a server grant prevents future feed and push operations after the server rechecks ACLs, but cannot erase a copy already delivered to a client. Push validation ignores client actor claims and stamps the authenticated actor; it rejects malformed/oversized envelopes, invalid revision identity/parent relationships, computed kinds, and common credential patterns. Feed responses apply workspace ACLs before exposing event IDs or bytes, use per-readable-scope sequences, bind HMAC cursors to actor/device/grants, and hash-chain event bytes. Phase 2 exposes pull routes and Phase 3 adds the authenticated push route. Imported Markdown remains untrusted inert data. Source originals require an explicit ACL-checked digest lookup; there is no automatic external fetching or model/network call.
# Replica HTTP exposure

Replica pull routes require a scoped revocable credential and expose only currently readable enrolled workspaces. Workspace enrollment failures intentionally share one generic response so unknown, retired, personal, and unauthorized workspace IDs cannot be distinguished. Read access is checked again on each fetch; a changed grant invalidates the scope version and requires a resync. Revocation and rotation stop serving immediately and delete server-side device records. A revoked client may still retain bytes already downloaded, so local replica deletion remains the client's responsibility.

Profile snapshots require `global:profile:read` and include accepted, non-sensitive insight items filtered to global statements and readable workspace labels. Fetch pages are capped at 200 events and 1 MiB; JSON request bodies are capped at 64 KiB. Blob bytes are served only from an enrolled readable workspace after SHA-256 verification. Replica HTTP routes are outside MCP tool discovery. Browser CSRF is not applicable to these bearer-authenticated machine routes; the existing origin policy still applies.

| Route | Auth | Size | Rate/admission | Version | CSRF |
|---|---|---|---|---|---|
| `POST /replica/v1/hello`, `/enroll`, `/unenroll`, `/fetch` | Scoped revocable bearer | JSON ≤64 KiB; fetch ≤200 events/1 MiB | 120 per credential/device/minute; fair admission | `v:1`; strict unknown-key rejection | Not applicable to machine bearer calls; Origin policy remains |
| `POST /replica/v1/push` | Scoped revocable bearer and enrolled writable scope | JSON ≤4 MiB; ≤100 operations | 120 per credential/device/minute; fair admission | `v:1`; strict operation schema | Same |
| `GET /replica/v1/blobs/<digest>` | Scoped bearer plus enrolled scope and device ID | Digest-verified bytes | Fair admission | Path digest must be SHA-256 | Same |
| `GET /replica/v1/profile` | Scoped bearer with profile read grant | Snapshot bounded to 1 MiB | Fair admission | ETag/revision hash | Same |
# Replica push threat model

Replica push is accepted only from scoped revocable HTTP credentials, never shared bearer tokens or OAuth identities. Requests pass through the common fair admission queue, are rate limited per credential/device, bounded to 4 MiB and 100 operations, and reject unknown fields. The server validates each operation using the Phase 1 validator, derives actor identity from the credential, checks active enrollment and current write access for each operation, rejects stale scope versions, and commits each operation through Vault. Idempotency binds the device/op ID to the canonical payload hash and returns the original result, including the authoritative revision bytes needed for client reconciliation. Conflict responses reveal only a readable current head ID. Computed profile and insight files remain pull-only; preference statements use the explicit typed path and return no root-file bytes.

Client-provided Markdown is untrusted data. It is size bounded, secret checked, and treated as content rather than instructions. Clients cannot submit actor stamps, journal events, server sequence numbers, server-computed kinds, or arbitrary revision ancestry. Local accepted-byte replacement is capability gated inside Vault and limited to an exact provisional candidate; it cannot be invoked via CLI/MCP/dashboard.

Client replica roots and token files are private (`0700` directories and `0600` files); this protects against other local users, not the signed-in account or disk loss. The token value is never stored in replica config or service arguments: config stores only the token-file path. Revoking/rotating the credential blocks future server access, but downloaded revisions and local pending writes remain on the client until locally removed. `mdb replica remove` unenrolls while retaining local data; `--purge-local` is explicit and requires confirmation. Do not enroll personal, wiki, shared, discoveries, or unrelated workspaces when their content should not be cached.


## Dashboard replica visibility

The loopback-only client dashboard exposes replica status, enrolled workspace identifiers, queue counts and conflict versions only to the local dashboard session. Status omits server URLs, device IDs, token paths and credential contents; daemon error text is redacted. Conflict Markdown is returned only to the authenticated local conflict view and the UI inserts it as text. Mutations use the dashboard session, same-origin/CSRF checks, and rate limits. Workspace enrollment errors are generic to avoid revealing whether a remote workspace exists. The owner dashboard exposes device enrollment and heartbeat summaries; unenrollment requires password re-authentication and is audited.

The local client dashboard exposes only the replica's enrolled workspace metadata and conflict view needed for local resolution. Conflict bodies are capped at 100 KB per side and rendered as text; Markdown and HTML are not interpreted. Replica workspace size is a bounded approximate count of the local workspace projection and journal-attributed revisions. Mutating dashboard routes require a session, same-origin request and CSRF marker; server-side device workspace unenrollment additionally requires password re-authentication and creates an audit entry. Dashboard payloads never include replica tokens or token-file paths.


Replica caches disclose the existing at-rest boundary: private directories use mode 0700 and private files use mode 0600, but replica data is not encrypted at rest. Revoking a credential stops future server access; it cannot erase revision or source bytes already cached on a client device. Source originals are fetched only on demand, are digest-checked, and are subject to the configured per-blob cache limit.
