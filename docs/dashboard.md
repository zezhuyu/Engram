# Local dashboard

Start the owner-only dashboard with `mdb dashboard [--host ADDR] [--port N] [--open] [--root PATH]`. Defaults come from `MDB_DASHBOARD_HOST` and `MDB_DASHBOARD_PORT`; flags take precedence. `MDB_DASHBOARD_ENABLED` controls availability at startup (default enabled). Accepted true values are `true`, `1`, `yes`, `on`; false values are `false`, `0`, `no`, `off` (case-insensitive; empty is the default). Any other value is an error. When disabled the command exits without binding. `mdb dashboard --reset-password` deletes the effective password record and sessions without starting a listener; the next start requires the printed one-time token URL to set a password again.

By default the dashboard binds exclusively to `127.0.0.1` on an ephemeral port (`0`). Host values must be IP literals assigned to a local interface, or wildcard `0.0.0.0`/`::`. The command prints the password file path, whether a password is set, and a URL containing a random 256-bit bootstrap/recovery token in its fragment. On first use, open the complete URL and set a password (12–256 characters, not the token). Later visits use the password; the bootstrap URL remains available for password setup after `--reset-password`. The token changes at every server restart, so old links stop working. Use `--open` to ask the host to open the URL. The server runs until stopped with Ctrl-C. Set `MDB_DASHBOARD_IDLE_MINUTES` to a positive number to enable idle shutdown.

The password record is stored independently of the vault: on macOS, `~/Library/Application Support/Engram/dashboard/auth.json`; on Linux, `${XDG_CONFIG_HOME:-~/.config}/engram/dashboard/auth.json`. Set `MDB_DASHBOARD_AUTH_FILE` to override the location. The containing directory is mode `0700` and the file is mode `0600`; writes use a synced temporary file and atomic rename. If the user-level file is absent and the legacy `<vault>/.mdb/dashboard/auth.json` exists, it is copied into the user-level location on first access and left intact. The effective file is used by `--reset-password` and password changes. Passwords must contain 12–256 characters, cannot be all whitespace, and cannot contain C0/C1 control characters. Leading or trailing whitespace is retained and counts toward the length; it is never silently trimmed. Passwords are hashed from their exact UTF-8 bytes without Unicode normalization, preserving existing hashes.

A non-loopback host such as a Tailscale interface address automatically enables remote mode. For example, `mdb dashboard --host 100.77.249.102 --port 8080` binds only that local interface. `mdb dashboard --allow-remote` remains shorthand for `--host 0.0.0.0`; wildcard binds print URLs for every non-internal IPv4 interface and `127.0.0.1`. It prints a prominent warning because traffic is plain HTTP: anyone who can reach the port and obtain the token has owner-level access to dashboard settings. Use only on a trusted LAN or VPN, and keep the token private. Do not expose the port to the public internet. Hostnames and addresses not assigned to a local interface are rejected.

## Browser security and privacy

The browser reads the bootstrap token from the fragment only for first-time password setup, removes the fragment from the address bar, and never stores it in browser storage or sends it in a request URL. Passwords are stored as scrypt hashes. Successful password login sets a random `HttpOnly; SameSite=Strict` session cookie with a 12-hour idle lifetime; activity extends the cookie, while server-side sessions expire after 12 hours idle or seven days maximum. Sessions survive dashboard and machine restarts, are stored as hashes of cookie ids in a `0600` `sessions.json` file next to `auth.json`, and at most eight are retained. Logout revokes the current session; sign-out-everywhere and password changes revoke all sessions. `mdb dashboard --reset-password` is the local recovery path.

Browser session requests include `X-Engram-Dashboard: 1`; state-changing session requests also require a same-origin `Origin`. Script and CLI clients can continue to use the bearer token. The server validates exactly one non-empty, syntactically safe `Host` header before routing, body parsing, or authentication on every route, including the page and static assets. Duplicate, comma-joined, empty/whitespace, or control-character values and HTTP/1.0 requests without Host receive `400 INVALID_HOST`. The allowlist also covers every route: a disallowed Host receives the same `403 HOST_NOT_ALLOWED` JSON body without page or asset content. Local-only mode accepts `localhost`, `127.0.0.1`, and bracketed `[::1]` with the listening port. Hostname matching is case-insensitive (`LOCALHOST` works); trailing-dot names and port mismatches are refused. Wildcard remote mode accepts loopback names, IP-literal Host values, and the machine hostname; a specific interface bind accepts only its configured address. Both reject unrelated DNS names to retain DNS-rebinding protection. The server limits JSON bodies to 64 KiB, API requests per minute, and failed bearer-token attempts to 10 per source IP per minute, restricts methods, and serves the existing strict Content Security Policy with no inline script or style. JSON bodies use strict parsing that rejects malformed JSON, duplicate object keys, and `__proto__` keys before route authentication. Password login applies a fixed minimum response time and per-IP/global exponential backoff with lockout after five failures. Hashed per-source counters and global counters are stored atomically in a mode-0600 `login-lockouts.json` next to `sessions.json`, so restarting the dashboard does not clear an active lockout. Unauthorized API calls receive 401; lockouts receive 429 with `Retry-After`.

The UI uses the local API only. Status data contains bounded counts, states, timestamps, and identifiers; it excludes document titles, snippets, provider key values, and raw failure details. Expensive vault and index verification run only after an explicit click. Model testing requires the configured network permission and sends the provider's synthetic connectivity prompt; it does not include vault content.

The password protects routine browser access; the bootstrap token is a first-setup/recovery credential and bearer credential for scripts. **OPEN_POLICY (GA-F-005):** the bootstrap bearer can create dashboard credentials while connector management requires a session; whether remote credential creation should require a session and re-authentication remains an owner decision. In remote mode, the dashboard is reachable on the configured non-loopback interface; wildcard binding exposes it on every network interface. Remote mode should use TLS for public or untrusted networks. The listener accepts `MDB_DASHBOARD_TLS_CERT` and `MDB_DASHBOARD_TLS_KEY`; remote dashboard admin credentials are disabled unless `MDB_DASHBOARD_REMOTE_ADMIN=true`. Plain HTTP remote admin is limited to a private RFC1918 or tailnet interface. See [dashboard-client.md](dashboard-client.md). IP-literal Host values are accepted by design, so Host validation is not an access-control boundary. Rate limiting slows guessing but does not replace network isolation. Remote mode does not protect a vault from a compromised local account or another process running as the same user.

Credential-file reads validate the configured path, then open with no-follow semantics and verify/read through that same file descriptor. Forwarded-address headers do not affect login lockout keys; the dashboard uses the socket peer address. Strict JSON parsing rejects nesting deeper than 256 levels as an invalid request.

Malformed request framing rejected by Node's HTTP parser is handled at the server boundary; malformed Host requests receive the same `400 INVALID_HOST` response as Host values that reach the route handler. The forwarded-header probe still reaches the global 429 lockout, but the persisted source map remains empty, so per-socket lockout persistence is not established by that result.

## Screens and settings

The page provides Overview, Knowledge, Wiki chat, Workspaces, Wiki review, Storage & index, Jobs & scheduler, Dream & wiki, Capture, Connections, Client settings, Settings, and Audit screens. Connections and Client settings appear when the local client dashboard is enabled. Status polls every 10 seconds while the tab is visible. Polling pauses in a hidden tab and backs off when the server is unreachable. A disconnected banner indicates a failed connection.

Visual QA captures are PNG contact sheets in [dashboard-screenshots](dashboard-screenshots/). Each page sheet shows 1440×900 and 500×900 views in light and dark themes; the chat sheet also shows empty, attached-file, and mid-conversation states. Settings has separate full-page light and dark captures that include Connectors and both credential sections. Captures use a temporary local vault and authenticated dashboard session; the mid-conversation example is ephemeral and the empty test vault returns no matching knowledge. No demo-vault data is included.

Knowledge lists use bounded cursor pages and support text, scope, kind, tag, and include-deleted filters. The list contains only actor-authorized metadata; opening a document loads its authorized body, visible links/backlinks, revision history, and selectable revision diffs. Create and edit preserve Markdown as inert text. The editor keeps the loaded revision ID as hidden state and sends it with every edit. A stale save returns `409 CONFLICT`; the editor shows the current title and body while retaining the draft, with actions to reapply the draft against the latest revision, reload the current version, or return to the document. A successful save or reapply returns to Knowledge with a success toast. PATCH, DELETE, and restore require a non-empty `expectedRevisionId`; missing or empty values return `400 INVALID_INPUT`, and stale values return `409 CONFLICT` without creating a revision. Delete creates a tombstone, displays the visible backlink count, and can be reversed by restoring a historical revision (which creates a new revision). History remains available for tombstones if their links are unavailable. Create, edit, delete, and restore accept idempotency keys. Document APIs cap JSON request bodies at 256 KiB; other dashboard routes retain the 64 KiB limit. Wiki pages may be directly edited by the owner; lifecycle retire, rename, and merge actions are submitted as proposals and reviewed separately. Approving merge or retire requires typing the action name. Workspace listing and creation are owner operations. Purge is not exposed.

All knowledge calls use the dashboard's existing actor-bound Engram client. Knowledge mutations append attempt and outcome records to the dashboard audit log. These summaries contain operation identifiers, revision identifiers, and a title truncated to 80 characters; document bodies are never audited. Markdown display uses text nodes/preformatted text, with no HTML passthrough. The existing CSP is unchanged. Browser session mutations still require same-origin requests; bearer-token clients remain supported.

Settings includes read-only Server and Security groups showing the effective bind, port, enablement source, and whether a password is set. The Security group supports password change and sign-out-everywhere. Changing bind or port requires restarting `mdb dashboard` with `--host`/`--port` (or environment defaults); the served UI cannot safely rebind the listener it depends on. Other settings are a fixed allowlist backed by the existing SDK/config setters. Each change is validated, checked against the current SHA-256 configuration etag, previewed with its risk, and then applied. Sensitive changes require typed confirmation. Environment-locked fields are read-only and show the variable name, never its value. The dashboard cannot edit ACLs, credentials, trust, environment overrides, binding, or other unsupported configuration.

Settings also includes OpenAI/ChatGPT Secure MCP Tunnel and Claude remote connector setup. The real MCP endpoint path is `/mcp`; the public base URL is owner-entered. Tunnel commands and ingress remain owner-managed: the dashboard never launches a tunnel, opens a port, or changes network exposure. ChatGPT uses a dedicated outbound tunnel-client profile forwarding to the loopback HTTP service. Claude.ai needs an independently approved public HTTPS adapter and OAuth setup; Claude Code can use `claude mcp add --transport http engram https://HOST/mcp`. A user-clicked connection test requests only `https://HOST/version`, rejects non-HTTPS/private destinations by default, pins the checked DNS address, refuses redirects, and reports only HTTP status and the server version.

Connector settings are stored atomically at `.mdb/dashboard/connectors.json` with mode `0600`. Secret values are write-only and API responses return only whether each is set; save confirmation is typed and audit entries contain connector/field names only. Scoped MCP credentials use the existing hash-only credential registry and owner permission validation. Their token is returned only at creation or rotation and is not present in inventory or audit responses. Revocation requires typing the credential ID. Connector management requires a logged-in dashboard session and same-origin CSRF header; requests retain the standard 64 KiB dashboard JSON limit. Treat connector values as local configuration, back up the vault securely, and keep all tunnel/OAuth secrets in a secret manager where possible.

Every setting mutation first appends an `attempt` record containing redacted old and proposed values. If that append fails, the setter is not called. A second `applied` or `failed` record captures the outcome. Records are stored append-only at `.mdb/dashboard/audit.jsonl`; the API shows the latest 200. This audit is operational configuration history only: configuration is not journaled knowledge, and the dashboard does not create Markdown revisions or journal events for config edits. Back up the audit file separately if that history matters.

The outcome append is necessarily after the existing config setter. If storage fails in that interval, a setting may have changed even though the request reports an audit error; the durable `attempt` record will remain without an outcome. Check the effective Settings values before retrying, and preserve the audit file for diagnosis.

## Wiki chat and source imports

Wiki chat searches only through the actor-bound Engram search API. Citations contain the exact document URI and revision ID; each cited revision is fetched through the same ACL-filtered client before it is returned. Chat turns stay in browser memory and are not written into the vault. “Use model” is optional. If a provider is ready but `model.allowNetwork` is off, selecting the switch opens a typed-consent dialog before asking the existing settings preview/apply endpoints to enable that audited setting. The dialog explains that the question and retrieved excerpts from pages the actor is authorised to read go to the configured provider; it excludes the rest of the vault and unrelated pages. The choice to use synthesis is kept in that browser tab only. The switch is available only when `describeModel` reports a ready provider and remote use is permitted by `model.allowNetwork`; remote providers still follow `model.allowPrivateContentToRemote`. When enabled, the chat shows the provider and notes that excerpts are sent. Each answer identifies whether it used model synthesis or deterministic retrieval. Other unavailable reasons appear beside the switch with a link to the Model provider settings. The shared model prompt policy marks documents as untrusted data, and the dashboard accepts only schema-valid output whose citations match the retrieved revisions. Model output remains untrusted and citations establish provenance, not truth. Without an available provider, chat returns deterministic retrieved excerpts and a clear unavailable reason.

The Add source controls accept pasted text or one explicit multipart file. The allowlist is `.md`, `.markdown`, `.txt`, `.json`, and `.pdf`; content type and extension must agree, UTF-8 text is checked, and PDFs must have the `%PDF-` signature. Upload size defaults to 8 MiB and can be changed with `MDB_DASHBOARD_UPLOAD_LIMIT_BYTES` (1 byte through 64 MiB). Filenames are reduced to a sanitized basename. The route never accepts a filesystem path and never fetches URLs mentioned in text. Because `Vault.ingest` currently takes a path, accepted bytes are written to a private mode-0700 `.mdb/scratch/dashboard-uploads` directory using mode-0600 generated files, ingested through Vault, then removed in a `finally` cleanup. Stable generated names and Vault idempotency make retries refer to the same immutable import. Redacted attempt/outcome audit entries record source and proposal identifiers, revision IDs, bounded titles and byte counts, never source bodies. A failed process may leave a scratch file; it is not canonical knowledge and can be removed after confirming no dashboard import is running.

“Propose wiki update from this source” creates a pending, evidence-linked `wiki_page` proposal. It does not create or update a page; an owner must review the proposal through Wiki review. The UI renders answers, citations, and source names through DOM text nodes. Chat has one active request per authenticated session, a bounded request size, a 45-second default provider timeout, and aborts model work when the client disconnects. The API returns citations only after ACL-filtered retrieval; inaccessible sources do not appear in snippets or citations.

## URL notes

Chat detects an HTTP(S) URL and offers an explicit “Read this URL with Claude/Codex” action. Before starting, the dashboard explains that the URL and page content are sent to the selected CLI's provider and asks for confirmation. URL notes are off by default. Settings → URL notes reports executable presence, version, and a local login-status result for each installed CLI; enabling or disabling requires typing `ENABLE URL NOTES` or `DISABLE URL NOTES`. A URL may be at most 2,048 characters, must have no embedded credentials, and must use HTTP(S). IP literals and DNS results that are loopback, private, link-local, metadata, or otherwise non-routable are rejected. DNS validation is best-effort and checks the initial hostname before the CLI runs.

The server runs at most one URL job at a time. Jobs use an empty mode-0700 temporary directory, a scrubbed environment, a two-minute timeout, bounded output, and process-group cancellation. Claude is invoked with print mode, restricted mode, only WebFetch enabled and explicitly allowed, prompts denied, JSON output, no session persistence, no settings sources, and no MCP configuration. Any non-empty JSON `permission_denials` array fails the run, even if Claude exits successfully. Codex uses `exec`, read-only sandbox, no approvals, ephemeral execution, ignored user configuration, live web search, and `--output-last-message`. The installed versions and exact verified arguments are documented in `dashboard-url-notes-smoke.md`. The CLI still uses its own login; the dashboard does not pass vault credentials to it. CLI output is treated as untrusted JSON and checked against bounded draft fields.

The completed draft stays in server memory and is shown as editable title, summary, key points, and quotes. No vault document is written before the owner approves it. Approval ingests a provenance source through Vault and then creates a normal note, or submits a wiki proposal for owner review. Provenance records the source URL, agent, retrieval time, and SHA-256 digest. Attempt, success, rejection, and failure audit entries contain only the URL host and SHA-256 hash of its path, plus the agent and outcome; query strings and page content are excluded. The browser displays all draft text through DOM text nodes. A cancelled or failed job writes no source or note.

## Wiki chat

Chat replies are ephemeral and authorized against the current actor before page text or snippets are used. An empty visible vault offers actions to create a Knowledge document or attach a source. Greetings and help prompts receive a deterministic local explanation with document/page counts and example questions; they do not call a model. Retrieval removes common stopwords, scores overlap against candidate titles and bodies, shows the best matching passage, and cites at most three relevant pages. A no-match reply offers up to five recent authorized pages. Optional synthesis is disabled with an actionable reason when the configured provider cannot be used; a failed synthesis leaves the local retrieval answer visible. Message text is rendered as text, with timestamps, copy controls, and citation links.

Codex CLI 0.166.0 ignored the attempted `sandbox_network_access` and `features.web_search` configuration keys during the authorized smoke; the final command uses its documented top-level `web_search="live"` override, with the read-only sandbox and no other network tool requested. Claude Code 2.1.308 returned `Not logged in · Please run /login` during its smoke; its argument profile was accepted, but a successful Claude page read could not be verified in that account state.

## Commands and limits

```sh
mdb dashboard
mdb dashboard --host 127.0.0.1 --port 8080 --open
mdb dashboard --host 100.77.249.102 --port 8080
mdb dashboard --root /path/to/vault
mdb verify
mdb index verify
mdb index rebuild
mdb jobs status
mdb storage status
```

Vault and index verification are explicit, potentially expensive actions. Rebuilding an index, recovery, reconciliation, backup/restore, cleanup, ACL changes, and credential or trust management remain CLI operations. The dashboard does not fetch external resources automatically. No provider means model-dependent functions remain unavailable; deterministic status and maintenance remain usable.
